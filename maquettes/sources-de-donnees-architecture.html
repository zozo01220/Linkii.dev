Comment les données voyagent

Une source externe n'est jamais lue par l'écran. Le serveur Linkii la lit, la range dans une table au format unique, en garde une copie, puis l'écran reçoit seulement les lignes et colonnes que la composition utilise.

Trois mots pour l'utilisateur

1 Connexion

« Où sont les données et comment y entrer. » Une adresse, une clé, un mot de passe. Partagée par tous les jeux de données de ce système.

2 Jeu de données

« Quelles données je veux. » Une requête qui donne toujours une table propre, avec un aperçu et une fréquence d'actualisation.

3 Liaison

« Où je les montre. » Un champ, une liste ou un indicateur dans une composition, glissé depuis le panneau Données.

Reste sur le serveur

  • Identifiants chiffrés, jamais envoyés à l'écran ni au navigateur
  • Requêtes et adresses des systèmes
  • Historique des lectures, erreurs, durées

Part vers l'écran

  • Uniquement les colonnes utilisées par la composition
  • Les lignes déjà filtrées pour cet écran
  • L'heure de la lecture, pour l'affichage hors ligne

Ce qui protège

  • Lecture seule : SELECT seulement, compte en lecture conseillé
  • Délai max 10 s, 5 000 lignes et 2 Mo par jeu
  • Adresses internes de Linkii refusées (SafeHttp)

Le contrat d'un connecteur

Ajouter un type de source (OData, MQTT, ERP…) revient à écrire un connecteur. Le reste (planification, copie, éditeur, écrans) ne change pas. Les intégrations actuelles (météo, RSS, capteurs) deviennent des jeux de données comme les autres.

IConnector Test(connexion) → « Connexion réussie » ou erreur Discover(connexion) → endpoints, tables, feuilles Read(connexion, requête) → Table Table // format unique, quel que soit le type columns : [{ key, label, type }] rows : [[…], […]] readAt, hash, source

Ce que reçoit l'écran

Déjà filtré (étage 2), trié, réduit aux trois colonnes utilisées. Le player ne connaît ni la base ni la requête.

{ "columns": ["salle", "statut", "prochaine"], "rows": [ ["Léman", "Libre", "14:00"], ["Jura", "Occupée", "15:30"] ], "readAt": "2026-10-29T13:42:05Z", "hash": "9c1e…" }

Surveillé : relu dès qu'il change

Votre système envoie un POST en JSON ou CSV à chaque changement. Linkii répond en moins d'une seconde, les écrans sont mis à jour aussitôt. En attente du premier envoi…

Une connexion, plusieurs jeux de données

Vous donnez l'accès une seule fois. Ensuite vous créez autant de jeux de données (tables, requêtes, endpoints) que nécessaire.

Vos identifiants

Chiffrés sur le serveur. Ils ne sont jamais envoyés aux écrans, ni réaffichés ici.

Lecture seule

Linkii ne fait que lire. Pour une base, créez un utilisateur qui n'a que le droit de lecture : le test le vérifie.

Le relais

Un service Windows ou Linux de quelques Mo, qui appelle Linkii (sortant, HTTPS). Aucun port à ouvrir. Un relais sert plusieurs bases.

Types détectés automatiquement, modifiables. Ils servent à l'éditeur : une colonne « Date et heure » se met en forme (14:00, demain, dans 5 min), une colonne « Image » remplit un emplacement d'image.
